    \textbf{Types of cohesion}

    \begin{itemize}
        \item Functional
        \begin{itemize}
            \item Facilities perform only one computation with no side effects
        \end{itemize}
        \item Layer
        \begin{itemize}
            \item Related services are kept together, everything else is kept out, and there is a strict hierarchy in which higher-level services can access only lower-level services. Accessing a service may result in side effects
        \end{itemize}
        \item Communicational
        \begin{itemize}
            \item Facilities for operating ont he same data are kept together
        \end{itemize}
        \item Sequential
        \begin{itemize}
            \item A set of procedures, which work in sequence to perform some computation, are kept together. Output is from one input to the next.
        \end{itemize}
        \item Procedural
        \begin{itemize}
            \item A set of procedures, which are called one after another, are kept together
        \end{itemize}
        \item Temporal
        \begin{itemize}
            \item Procedures used in the same general phase of execution, such as initialization or termination, are kept together
        \end{itemize}
        \item Utility
        \begin{itemize}
            \item Related utilities are kept together, when there is no way to group them using a stronger form of cohesion
        \end{itemize}
    \end{itemize}

    \textbf{Types of coupling}
    \begin{itemize}
        \item Content
        \begin{itemize}
            \item Component modifies internal data of another
        \end{itemize}
        \item Common / global
        \begin{itemize}
            \item Using global variables; all modules using the global variable are coupled
        \end{itemize}
        \item Control
        \begin{itemize}
            \item One module (A) directly controls the other (B) by passing information on what B should do; e.g., using a ``flag'' that defines what B should do
        \end{itemize}
        \item Data
        \begin{itemize}
            \item One module sharing data with another module; e.g., via passing parameters
        \end{itemize}
        \item External
        \begin{itemize}
            \item A dependency exists to elements outside the scope of the system, such as the operating system, shared libraries or the hardware.
        \end{itemize}
        \item Temporal
        \begin{itemize}
            \item Two actions are bundled together just because they happen to occur at the same time
        \end{itemize}
        \item Inclusion / import
        \begin{itemize}
            \item Including a tile or importing a package
        \end{itemize}
    \end{itemize}

    \begin{enumerate}

                \item Deploy all logical components that make up the application as one unit
                \item Application runs as one process
            \end{itemize}
            \item Distributed units
            \begin{itemize}
                \item Application consists of independent logical components
                \item Logical components run as individual processes
                \item Communicate over the network
            \end{itemize}
        \end{itemize}
    \end{enumerate}

    \uline{Layered Architecture}

    Software is organized as layers of components
    
    \begin{itemize}
        \item Supports independent development and evolution of different system parts
        \item No lower-level layer will make a call to a upper-level layer
        \item Comprises one or more layers for the software under development, with each layer having a distinct and specific responsiblity
    \end{itemize}

    \begin{Figure}
       \centering
       \includegraphics[width=0.4\linewidth]{layered_architecture.png}
    \end{Figure}

    Buys:

    \begin{itemize}
        \item Structure-enforced separation of concerns
        \item Modifiability within the layer
        \begin{itemize}
            \item Can swap technologies without affecting other layers
            \item E.g. swap oracle db with mysql
        \end{itemize}
        \item Testability - mockk the layer below to test the current layer
    \end{itemize}

    Costs:
    \begin{itemize}
        \item Deployability - all or nothing (cuz everyt is one process)
        \item No independent scaling
        \item No feature ownership - teams organized by layers
        \item Change amplification - one feature change impacts all layers (because one feature cuts across multiple layers)
    \end{itemize}

    Doesn't impact usability

    \uline{Pipe and Filter}

    \begin{itemize}
        \item Linear
        \item Data enters the system and flows through the components one at a time until the data is assigned to some final destination (data sink)
        \item Components: Filters, data source, data sink; each component has
        \begin{itemize}
            \item Set of inputs (read)
            \item Set of outputs (produce)
        \end{itemize}
        \item Filter:
        \begin{itemize}
            \item Transforms the input streams
            \item Computes incrementally, so output begins before the input is consumed
            \item Independent, share no state with other filters
        \end{itemize}
        \item Connectors: Pipes
        \begin{itemize}
            \item Each pipe transmits outputs of one filter to inputs of another
        \end{itemize}
        \item Divide the application's task into several self-contained data process steps and connect these steps to a data processing pipeline via intermediate data buffers
        \item Data flows in streams: good for processing of images, audio, video, or batch data
        \item Good for limited user interaction, like batch processing systems
    \end{itemize}

    \begin{Figure}
       \centering
       \includegraphics[width=\linewidth]{pipe_and_filter.png}
    \end{Figure}

    \begin{Figure}
       \centering
       \includegraphics[width=\linewidth]{pipe_and_filter_2.png}
    \end{Figure}

    Buys:

    \begin{itemize}
        \item Scalability - due to stateless nature of the filter, we can replicate any filter
        \item Deployability - replace any filter, as long as the contract on the data format remains the same
        \item Testability - no side effects $\Rightarrow$ independent mocking / testing
        \item Reuse - same filter can be applied in a different pipeline
    \end{itemize}

    Costs:
    
    \begin{itemize}
        \item Latency grows with every stage - may also be a result of data transformation
        \item Usability - no feedback until we check the sink
        \item Cannot natively handle partial failures
    \end{itemize}

    Choose when work involves batch / stream transformation and throughput (volume) matters more than latency (speed)

        \end{itemize}

        \end{itemize}

    Costs:
    \begin{itemize}
        \item Performance - multiple hops for a single view update
        \item ``Fat controller'' - requests flow through the controller can lead to new logic being accumulated in the controller
    \end{itemize}

        \end{itemize}
        \item Intention: Provide uniform interoperability, between different applications on the internet

        \end{itemize}

    \uline{6 REST arhitecture constraints:}

    \begin{enumerate}
        \item Client-server
        \item \textbf{Stateless}
        \item Layered system
        \item Cacheable
        \item \textbf{Uniform interface}
        \item Code-on-demand (only optional constraint)
    \end{enumerate}

    \uline{Constraint: client-server}
    
    REST applications should have a client-server architecture for separation
    of concerns (client not concerned with data storage of the resource, server
    not concerned with user interface or user state)
    \begin{itemize}
        \item Portability of user interface
        \item Scalability of server components
        \item Evolve independently to support internet-scale requirements
    \end{itemize}

    \uline{Constraint: stateless}

    Each interaction between a client and the server has to be entirely self-contained
    (full information contained as part of the query params, headers, or URI)
    \begin{itemize}
        \item Server must not rely on information from previous requests
        \item No session is maintained on the server side
        \item Server is bound by the number of concurrent requests and not the
        number of clients interacting
        \item Reason: to improve
        \begin{itemize}
            \item scalability (server can quickly free resources
            to serve additional requests)
            \item reliability (can recover from partial failures)
            \item Monitoring (only look at the single request data to analyze the request)
        \end{itemize}
    \end{itemize}

    \uline{Constraint: cacheable}

    Response from server should include if the data is cacheable (and for how long) or not.
    Client returns data from its cache in response to subsequent equivalent requests.

    \begin{itemize}
        \item Reason: to improve network efficiency
        \begin{itemize}
            \item Potentially eliminate some interactions
            \item Improves efficiency, user-perceived performance
        \end{itemize}
        \item (-) Client can potentially receive stale data
    \end{itemize}

    \uline{Constraint: layered system}

    Application must be organized as a (network) layered system.

    \begin{itemize}
        \item Each layer cannot see beyond the immediate neighbor
        \item A client does not know and should not assume it has a direct connection to the server
        \item Improved component complexity by restricting complexity to individual layers
        \item Intermediary servers may improve system availability and performance
        \begin{itemize}
            \item E.g., by enabling load-balancing, caching
        \end{itemize}
        \item Provide data transformation \& filtering
        \item (-) overall system complexity increases
    \end{itemize}

    \begin{Figure}
       \centering
       \includegraphics[width=\linewidth]{layered_system.png}
    \end{Figure}

    \uline{Constraint: uniform interface}

    There should be a uniform way of interacting with a given server irrespective
    of device or type of application.

    \begin{itemize}
        \item Principle: Generality to the component interface
        \begin{itemize}
            \item Implementations are decoupled from the services they provide
            \item System is free from unnatural restrictions and limitations
        \end{itemize}
        \item Should be efficient for large-grained hypermedia data transfer
        \item Exploits HTTP/HTTPS requests and responses
        \begin{itemize}
            \item Requests: GET, PUT, POST, DELETE
            \item Responses: HTTP status codes (e.g. 200 OK, 404 NOT FOUND)
            \item Use the HTTP body to transfer the resource representation
        \end{itemize}
        \item Anything can be a resource (resource-based)
        \begin{itemize}
            \item Key abstraction of information in REST
            \item E.g. document, image, user, etc.
        \end{itemize}
        \item Resource is a conceptual mapping to a set of identities
        \item Resources are identified using stable, global, and unique resource identifiers
        
        \verb|/device-management/managed-devices/{id}|
        \item Components perform operations on resource representations
        \begin{itemize}
            \item Representation consists of data, metadata describing the data
            \item Client has representation of resource and contains enough information
            to modify the resource on the server
            \item \verb|HTTP DELETE|

            \verb|/device-management/managed-devices/{id}|
        \end{itemize}
        \item Recollect: HTTP operations
        \item Content negotiation
        \begin{itemize}
            \item If uniform representation, how does REST handle heterogeneous data like text,
            images, video, PDFs?
            \begin{itemize}
                \item Use HTTP Content-Type header (MIME Types)
            \end{itemize}
        \end{itemize}
        \item Self-describing
        \begin{itemize}
            \item For interactions with resources through the uniform interface, REST needs self-describing messages
            \begin{itemize}
                \item Each message includes enough information to describe how to process the message
                so that server can easily analyze the request.
            \end{itemize}
            \item Components can get a complete understanding of resources or relevant states
            by just inspecting representations
            \item Hypermedia driving application state
            \begin{itemize}
                \item Representations that are exchanged should be linked
                \begin{itemize}
                    \item Clients that need the resource can discover them and obtain them from the links
                    \item These links enable exposing new resources and application state transitions
                \end{itemize}
            \end{itemize}
        \end{itemize}
    \end{itemize}
    \begin{verbatim}
    {
        "id": 123,
        "status": "PAID",
        "links": {
            "self": "/orders/123",
            "cancel": "/orders/123/cancellation",
            "refund": "/orders/123/refunds"
        }
    }
    \end{verbatim}

    Client does not need to know in advance that a paid order can be cancelled or refunded, or guess the URL structure.
    The server provides this information directly. 

    \uline{Constraint: code-on-demand}

    (Optionally) allow client functionality to be extended by downloading executable code 
    (e.g. applets, js code)

    \textbf{Advantages and disadvantages of REST}

    \begin{itemize}
        \item Advantages
        \begin{itemize}
            \item Systems that are less tightly coupled (uniform interface with
            self-contained messages $\Rightarrow$ depend only on the interface, not on internal implementation details)
            \begin{itemize}
                \item Allows for swapping, upgrading, or replacing components without affecting the system
            \end{itemize}
            \item Provides scalability, usability, accessibility, and
            
            mashup-ability
            \item New media types can be added without breaking the clients (through content negotiation)
        \end{itemize}
        \item Disadvantages
        \begin{itemize}
            \item Weak contract enforcement - no built-in typing; runtime errors (e.g.
            if client requests a pdf, no guarantee that what it receives is actually a pdf.
            Solely the client's responsibillity to check and handle that)
            \item Being stateless may decrease network performance by increasing the repetitive data sent in series of queries
            \item Using URI may degrade efficiency, since information is transferred in a standardized form rather than one which is specific to an application's needs.
        \end{itemize}
    \end{itemize}
